# Bassani Health Portal — Claude Code Instructions

This is the single source of truth for how to build and extend this system. Read this before making any decision. Everything here reflects confirmed direction from the product owner.

---

## What This System Is

The Bassani Health portal is a B2B sales and reseller portal for a licensed medicinal cannabis distributor in South Africa. It sits as a middleware layer between internal staff/resellers (who use it) and Odoo (which stores all financial and inventory data) — actually running **Odoo 19.0** on the live instance (confirmed live via `common.version()`, 2026-08-11; this file previously said v17, which was stale and had drifted from what the third-party host, `multisaas-odoo-bassani-health.odoo.com`, was actually running — see the `stock.move` field-naming note under Key Business Rules for why that mattered).

**Roles in the system:**
- `super_admin` — seeded from Railway env vars, unconditional access
- `admin` — operations staff, granular permission-gated
- `sales` — sales ticket workflow only (Merveille)
- `orders_clerk` — packing pipeline only (Tshidi)
- `finance` — deposit/payment confirmation only (Kashi, Ragini)
- `qa_manager` — QA approval on orders (Cullen Grant)
- `responsible_pharmacist` — RP approval on orders (Rookshanna Hussain)
- `warehouse_supervisor` — packing floor supervision
- `packer` — packing floor, own orders only
- `vault_custodian` — GACP production vault only (Patricia): batch ID generation + vault movements; sees nothing of the commercial pipeline
- `reseller` — external partners who place orders for their customers
- `customer` — self-service login for an already-approved customer (Phase 25). Admin-provisioned per Odoo contact, not self-registered; multiple logins can share one company account. Places its own orders and views its own invoices through the same pipeline as everyone else; never commission-eligible

## Architecture Principles — Non-Negotiable

These govern every decision. Do not deviate from them.

**1. Odoo is the financial source of truth.**
Every invoice, payment, order, and stock figure must originate in or be confirmed by Odoo. The portal never becomes a parallel ledger. All financial writes go through Odoo via XML-RPC.

**2. The portal is the main point of access — Odoo is invisible to staff.**
Staff should never need to log into Odoo for routine operations. Any step in the business workflow that requires opening Odoo is an unfinished portal feature, not an acceptable design choice. When a field-parity gap is found (an Odoo field shown but not editable in the portal), treat it as in-scope work.

**3. The portal maps to how the business works, not how Odoo works.**
The natural business workflow is: inquiry → quote → customer acceptance → deposit → fulfilment → collection. The portal expresses this in business language. Never expose Odoo's internal language (sale.order.state, account.move, stock.picking) to users.

**4. The ticket system is the single processing pipeline for all orders.**
Every sale.order — whether placed by a reseller, by staff, or converted from an inquiry — flows through Sales → Orders (packing board) → QA/RP → Finance. No order is processed outside this pipeline.

**5. MongoDB handles portal-layer concerns only.**
Reseller profiles, commission records, ownership mappings, onboarding applications, audit logs, tickets, settings, and customer metadata (e.g. `samples_account` flag) belong in MongoDB. Financial records (orders, invoices, payments) live in Odoo. Customer-level portal flags use the `customer_metadata` collection keyed by `odoo_partner_id`.

**6. All Odoo reads and writes are warehouse- and company-scoped.**
Bassani operates across multiple warehouses belonging to different Odoo companies. Every stock read, tax lookup, and record creation must be scoped to the resolved warehouse's company. Use `get_company_id()` and `company_context()` from `warehouse_context.py` — never bypass them.

**7. Every admin action is audit-logged.**
Every state change on a financial record captures actor, timestamp, IP, and before/after values. Use `audit_log()` from `middleware/audit.py` — this is the single canonical writer. Never add a second writer.

**8. Background tasks do not block API responses.**
Emails, push notifications, and non-critical writes always fire via FastAPI `BackgroundTasks`.

**9. All commission payments must produce an Odoo vendor bill.**
No statement can be marked paid without a corresponding `account.move` in Odoo.

**10. Everything runs on Railway.**
No new external services without an explicit decision. Approved additions: Resend (email), Sentry (errors), Cloudflare R2 (document storage), Google Places API (address autocomplete — proxied server-side via `places_routes.py`, key stored as `GOOGLE_PLACES_API_KEY` Railway env var, never exposed to the browser).

**Key files:**
- `backend/server.py` — FastAPI app, startup events, SPA catch-all route. The catch-all uses `os.path.realpath` confinement: any resolved path outside the static build directory silently serves `index.html` (path traversal protection). `log_requests` middleware logs `client_ip` on every request (added 2026-08-04) — only meaningful because `railway.toml`'s `startCommand` now passes `--proxy-headers --forwarded-allow-ips='*'` to uvicorn; without that flag `request.client.host` is Railway's own edge proxy for every request, not the real visitor, which also silently broke `slowapi`'s per-IP rate limiting (see Phase 1.4) into one shared bucket across all traffic.
- `backend/odoo_client.py` — the XML-RPC connection (`odoo()`, `OdooClient`) every other backend file goes through for model CRUD. **`fetch_report_pdf(report_name, res_ids)`** (2026-08-14) is a second, separate connection path — session-cookie HTTP, not XML-RPC — for the one thing XML-RPC genuinely cannot do: fetch a rendered report's PDF bytes. Odoo's XML-RPC dispatcher rejects calling `ir.actions.report._render_qweb_pdf` (a private, underscore-prefixed method) remotely with "Private methods ... cannot be called remotely" — this had silently always worked before because older Odoo XML-RPC didn't enforce the public/private boundary, and broke the automatic pro-forma invoice email (8.47) the moment that enforcement landed. There is no public XML-RPC equivalent; Odoo's own web client fetches reports the same way this does (`GET /report/pdf/<report>/<ids>` against an authenticated session), so this isn't a workaround, it's the actual supported mechanism, just reimplemented outside a browser. Two things had to be right for this to work, both live-verified before shipping: the report's own technical name had drifted (`sale.report_saleorder_pro_forma_invoice` → `sale.report_saleorder_pro_forma` on this Odoo version — verify directly against `ir.actions.report` if reusing this for another report, don't assume the old name), and a fresh web session defaults to the user's single primary company, which 403s ("doesn't have 'read' access ... multi-company issue") on any record belonging to a different company — fixed by passing every company the service account can see back in via the `context=` query param (`allowed_company_ids`, captured once at login from `/web/session/authenticate`'s response) on every request. Session cookie is cached and one-shot re-authenticated on expiry (detected via response content-type, not status code — an expired/wrong-company session redirects to an HTML login page with a `200`, not a `4xx`).
- `backend/auth.py` — `require_permission()`, `require_admin()`, role/permission constants
- `backend/middleware/audit.py` — single canonical `audit_log()` function. `before`/`after`/`detail` are sanitized (`sanitize_for_json()`, recursively converts any raw `ObjectId` to `str`) before insert — a real bug hit this in production (2026-07-30): `parent_category_routes.py`'s create endpoint reused the same dict it had just passed to `insert_one()`, which pymongo mutates in place to add a raw `ObjectId _id` key, so the stored `after` snapshot silently contained one. It writes to Mongo fine (BSON handles ObjectId natively) but 500s the entire audit list on read, since `jsonable_encoder` can't serialize a bare `ObjectId`. `audit_routes.py`'s `GET /` also runs every returned row back through `sanitize_for_json()` so historical rows written before this fix self-heal on read, rather than needing a data migration — audit history is never deleted to work around a bad row.
- `backend/services/email_service.py` — all transactional email templates and send logic. Deep links into the portal always use `f"{settings.portal_url}/..."` — `/applications/{app_id}` (onboarding), `/orders/{order_id}/passport` (Order Passport — first adopted by the QA/RP approval-needed emails), `/orders-tickets` and `/orders/backorders` (list-level links used by digest emails, since digests list multiple orders and don't deep-link per row), `/recurring/{token}` (recurring order customer review/accept, 8.46). `send_deposit_due_proforma()` (8.47) attaches a PDF fetched live from Odoo — follows the same `attachments=[{"filename":..., "content": list(bytes)}]` pattern as `send_customer_welcome_pack`. `send_order_confirmed_partial_customer()` (2026-08-22) is the customer-role counterpart to `send_order_confirmed_partial()` — see the Order pipeline business rule above for why only this one reseller-facing milestone got a customer twin, not all of them.
- `backend/services/scheduler.py` — time-based notification triggers no user action fires: 4-hour application-stall escalation (interval poll, every 30 min), three 17:00 SAST daily digests (outstanding QA/RP inspections, backorders, and — added 2026-08-21 — Manufacturing Orders still in progress, `run_mo_digest`), and two recurring-order jobs (8.46) — `generate_recurring_notices` (08:00 SAST, T-2-day draft+ticket+email generation) and `expire_unaccepted_occurrences` (18:00 SAST, skip-and-continue sweep for no-response occurrences), both implemented in `routes/recurring_order_routes.py` and just registered here. `_daily_loop`/`_sleep_until` are the only "run at a specific wall-clock time" mechanism in the codebase (fixed UTC+2 offset, no `zoneinfo`/tzdata dependency — SAST has no DST); `_interval_loop` mirrors the existing 22.1 payment-check loop shape. Started once from a `server.py` startup event. Recipients are read directly from `portal_settings.email_routing` (matching `bank_recon_service.py`'s existing convention for services-layer code, rather than importing the `routes.settings_routes` helper). **`run_mo_digest`** is the one digest that queries Odoo directly (`mrp.production`, `state not in ["done","cancel"]`) rather than Mongo — domain also requires `origin like "S0"` (Bassani's sale.order naming convention) specifically to exclude the unrelated vault/manicuring-lab MOs (`services/vault_odoo.py`), a different feature that also writes `mrp.production` but has nothing to do with customer-order replenishment.
- `backend/routes/settings_routes.py` — `EmailRoutingConfig` / `get_email_routing()`: the single MongoDB doc (`portal_settings._id: "email_routing"`) backing every configurable notification recipient list in the app (18 configurable keys as of 2026-08-22's `order_confirmed_partial_customer` addition — recurring order accepted/needs-confirm/declined/skipped are each their own key; "needs confirm" was split out from "accepted" the same day once it became clear a credit-limit block needing a human is a different urgency/audience than a plain FYI). Adding a new notification type means one new field here plus one new `ROUTING_KEYS` entry in `EmailSettings.js` — never hardcode a recipient address in a route file. `POST /email-routing/test` (8.48) sends a real template with fabricated dummy data to an admin-entered address — `TEST_EMAIL_SENDERS` is a dict of one lambda per `ROUTING_KEYS` entry (21 entries — the 18 configurable keys plus 3 preview-only entries with no `EmailRoutingConfig` field, since those always go straight to whichever customer the record already resolves to rather than a configurable staff list: `order_ready_customer`, `order_confirmed_partial_customer`, and `recurring_order_upcoming`); adding a notification type means adding one lambda here too, or the new key's Send Test button 400s. `order_cc` isn't its own template (it's a `cc=` add-on to reseller order emails) so its test previews via `send_order_confirmed` instead.
- `backend/warehouse_context.py` — `get_company_id()`, `company_context()`, and `resolve_warehouse_id(current_user)`, the single source of truth for which `stock.warehouse` a request is scoped to. **2026-08-04:** unified onto one model for every internal role — the top-nav switcher (`active_warehouse_id`, self-service `PUT /api/users/me/warehouse`) is now open to all internal roles, not just admin/super_admin; it falls back to a fixed `warehouse_id` for roles that have one pinned (warehouse_supervisor/packer/vault_custodian's assigned floor), then the global admin-set default. Reseller stays a separate branch — external role, fixed to their reseller profile's warehouse, no switcher. **Customer (Phase 25, 2026-08-21)** is its own branch too — fixed to an admin-pinned `warehouse_id` on the company's `customer_metadata` doc (shared by every login under that company), falling back to the global default; deliberately does not inherit a linked reseller's warehouse.
- `backend/routes/order_routes.py` — order pipeline, stock-check endpoint (`invoice_policy_block` logic here). Reseller visibility/access (list, detail, passport, confirm) and commission crediting at confirm time are all resolved via `backend/ownership.py`'s `customer_ownership` lookups (7.13), not `order.reseller_id`/`order_commissions.reseller_id` equality — those fields are kept only for the "who placed this" traceability display (8.34). `create_order` also server-side-enforces that a reseller may only place orders for their own linked customers. **Customer role (Phase 25, 2026-08-21):** parallel branches in `create_order`/`list_orders`/`get_order`/`get_order_passport`, simpler than the reseller ones — a single fixed equality check against `current_user["customer_company_partner_id"]` rather than an owned-partner-id set, since a customer login only ever represents one company. `PUT /{order_id}/confirm` is now a thin wrapper around `_confirm_order_core()` (8.47) — extracted so `public_routes.py`'s recurring-order accept endpoint (8.46) can call the exact same confirm logic with a synthetic system actor instead of a real `current_user`. `_confirm_order_core` advances the linked ticket to `awaiting_deposit` and does **not** queue the packing board — that's `_queue_packing_board()`, a separate function only called from `ticket_routes.py`'s `register-deposit` endpoint once a 50% deposit is actually registered (the universal gate, 8.47), and from `ticket_routes.py`'s `update_ticket_stage` (Admin Override) when moving a ticket to `confirmed_wip` with no existing `packing_board` entry for its order. **`_queue_packing_board` raises on failure rather than silently no-op'ing** (2026-08-11 fix — most commonly Odoo not having generated the order's delivery yet at the moment it ran): a confirmed order can sit at `awaiting_deposit` with a deposit already registered in Odoo but no packing board card for staff to act on, and nothing previously surfaced that. Callers never let this failure block or roll back anything already committed in Odoo (the deposit itself, or the order confirm) — they instead persist `packing_board_queue_error`/`packing_board_queue_failed_at` on the ticket (cleared automatically on a later successful call) so it stays visibly flagged (red banner on the ticket detail page, "Not Queued" badge on the ticket list) until an admin retries via Admin Override. Both functions live in this file and are imported by `ticket_routes.py`/`public_routes.py`/`recurring_order_routes.py` — none of those are imported back by `order_routes.py`, so there's no cycle. `GET /` (`list_orders`, the Orders screen) is now warehouse-scoped via `resolve_warehouse_id()` (2026-08-04 fix — it previously had no warehouse filter at all, so the Orders screen showed every order regardless of the selected warehouse; the frontend's `Orders()` load callback in `Views.js` also didn't re-fetch on warehouse switch, since `user.active_warehouse_id` wasn't in its `useCallback` deps — both fixed together). **`GET /{order_id}/quote-pdf` and `GET /{order_id}/deliveries/{picking_id}/pdf`** (8.54) stream Odoo's own rendered PDFs (`sale.report_saleorder`, `stock.report_deliveryslip`) via `fetch_report_pdf()` — the delivery-slip route confirms `picking.sale_id` actually matches `order_id` first so a stray `picking_id` can't be probed directly. `backend/routes/invoice_routes.py` has the matching `GET /{invoice_id}/pdf` (`account.report_invoice_with_payments`) for the real Odoo invoice PDF — distinct from that same file's `GET /{invoice_id}`, which powers the portal's own in-browser `InvoiceView` rendering (`Invoices.js`) and was and remains unaffected by any of this, since it never called Odoo's report engine at all.
- `backend/routes/product_routes.py` — product list (`category_id` int param for picker drawer), categories endpoint, `GET /{product_id}/lots` (in-stock lot list with qty aggregated from `stock.quant`, expiry from `stock.lot`). `PRODUCT_FIELDS` includes `image_128` (base64 thumbnail only — never the full `image_1920` — in any list/read response, keeping payload size sane). `POST /{product_id}/image` (multipart) and `DELETE /{product_id}/image`, both `products.manage`-gated, write/clear `product.template.image_1920` in Odoo; Odoo's ORM auto-derives and resizes `image_1024`/`512`/`256`/`128` on write, so the portal never resizes client-side. Image lives at template level (shared across variants), resolved the same `product.product` → `product_tmpl_id` way as `update_product`/`set_product_barcode`. `_apply_pending_gtin_fallback()` (2026-08-03) backfills `barcode`/`barcode_pending_sync: true` on any Odoo-fetched product with no barcode, from a matching `gtin_pool` entry that's `status: "assigned"` but `odoo_synced: false` — see `gtin_pool_routes.py` below for why that state exists. Without this, a GTIN assigned from the pool but not yet synced to Odoo (e.g. an Odoo access-rights gap on that product's company) would show "+ Set GTIN" on the Products list and block GS1/plain-barcode generation despite the reservation being real and known. Called once in `list_products()`'s single return point (covers both the search and non-search code paths). `GS1LabelModal.js`/`BarcodeExportModal.js` both consume this same product object, so they inherit the fallback automatically and show their own amber "not yet saved to Odoo" notice when `barcode_pending_sync` is true. **On Hand vs Forecasted (2026-08-05):** `list_products()` resolves the caller's warehouse once up front (before any domain filter, including the early empty-catalog returns) and always returns `warehouse_id`/`warehouse_name` alongside `products`/`total`, so any screen can show which warehouse its stock figures came from without re-deriving it. `in_stock_only` filters on `qty_available` (On Hand — physical units actually in the warehouse right now); the new `incoming_only` (8.51) filters the opposite gap — `qty_available <= 0` and `virtual_available` (Forecasted = On Hand + open incoming POs/transfers − open outgoing reservations) `> 0`, i.e. nothing on the shelf yet but Odoo is expecting stock. `GET /{product_id}/reservations` (admin-only) explains a Forecasted-below-On-Hand gap via open `sale.order.line`s; the new `GET /{product_id}/incoming` (8.51) is its mirror for a Forecasted-above-On-Hand gap, reading confirmed (`state in ["purchase","done"]`) `purchase.order.line`s not yet fully received — draft/sent POs are excluded since they haven't generated a stock move yet and so don't feed `virtual_available` at all.
- `backend/routes/label_routes.py` — GS1 label printing: printer CRUD (`/api/labels/printers`) + ZPL print endpoint (`/api/labels/gs1/print`). Printers stored in MongoDB `portal_settings` `_id: "label_printers"`.
- `backend/routes/gtin_pool_routes.py` — GTIN Pool management: bulk-add, list, assign to Odoo product, unassign, delete. Collection: `gtin_pool`. Assignment writes to Odoo `product.template.barcode`. The Odoo write is best-effort, not a hard gate (2026-08-03): if it fails (e.g. the API service account lacks write access to that product's company — a known Odoo multi-company access-rights gap, not a portal bug), the assignment/unassignment still completes in the portal so a GTIN is never stuck on an Odoo-side issue. `odoo_synced`/`sync_error` on the `gtin_pool` doc track whether the two sides actually agree, surfaced as an amber "Not synced to Odoo" badge in `GTINPool.js` with a **Retry Sync** action (`POST /{gtin}/retry-sync`) once the Odoo issue is resolved — never silently treated as fully done. Until synced, `product_routes.py`'s `_apply_pending_gtin_fallback()` reads the unsynced `gtin_pool` entry back onto the product list response so the reservation is still usable (Products list, GS1 labels, barcode export) rather than looking unset.
- `backend/routes/search_routes.py` — `GET /api/search/global?q=` — smart dispatch: 13–14 digit GTIN → product barcode lookup; sale.order name → Order Passport (`/orders/{id}/passport`); account.move name → resolves linked SO via `invoice_origin` and navigates to passport. Requires `require_admin`.
- `backend/routes/production_routes.py` — Phase 13.0 vault module: product shortcodes (`product_shortcodes`, seeded from `backend/data/product_shortcodes.json`; `import_ref` per product from `import_product_refs.json`), import suppliers (`import_suppliers`, seeded from `import_suppliers.json`), batch generator + registry (`batch_registry`, BH families only via `POST /batches` — **the `import` family is refused there** (422), created solely inside `_create_import_batch`/`receive_import` so an imported batch can never exist without its `s6_receipts` entry), vault movements + ledger (`vault_movements`), S6 receiving (`POST /vault/receive-import` — one action creates BI batch + vault receive + `s6_receipts` register entry; `GET /s6-register`), GACP readiness probe (`GET /odoo-probe`), staged-queue sync (`POST /sync-staged`), test-data purge (`POST /purge-test-data`, super admin, blocked once records are Odoo-synced, also clears `batch_balances`). S6 receipts are quarantined until RP release (`POST /s6/{id}/release|query`, `production.rp_release`; flag resolution via `/s6/{id}/resolve-flag`, `production.manage`); the quarantine gate in `create_movement` denies by default — an import-family batch with no `s6_receipts` record at all is blocked, not silently allowed. **Ledger balances are materialized (13.0.9), not recomputed per read:** `batch_balances` (one doc per `batch_id`) is updated incrementally by `_ledger_bump()`/`_ledger_manicuring_out_delta()` inside `create_movement`/`receive_import`, once per movement; `GET /vault/ledger` just reads it. `_recompute_all_balances()` holds the original full-history-replay algorithm as an on-demand reconciliation tool (`POST /vault/rebuild-ledger`, `production.manage`) — never call it per-request, it's O(all movements ever). **Pagination (13.0.9):** `GET /batches/grouped` is a Mongo aggregation that groups `batch_registry` by `base_batch_id` and paginates over the group count (never the raw stage rows — that would split one physical batch across pages); `GET /vault/ledger` additionally accepts `group_skip`/`group_limit` and returns a paginated `groups`/`total_groups` pair grouped in Python from the same `batch_balances` fetch, alongside the full unpaginated `rows` (still needed for the Record Movement form's point-balance lookups). `GET /vault/movements` and `GET /s6-register` already had working `skip`/`limit`/`total`. Permissions: `production.batch_generate` / `production.vault` / `production.rp_release` / `production.manage`.
- `backend/services/batch_id.py` — the single deterministic V6 batch ID implementation: 4 prefix families (`BH`/`BHAPI`/`BHB`/`BHG`), stage suffixes REPLACE each other (`-U` → `-M`, never stacked). Never re-implement ID formatting elsewhere.
- `backend/services/vault_odoo.py` — `VaultOdooWriter`: sole Odoo gateway for the vault module. `GACP_ODOO_WRITES=off` (default) stages every op (exact intended payload stored on the movement doc, `odoo_sync: "staged"`); `on` executes live (internal transfers, no-BoM `mrp.production` for the manicuring split, goods receipts against linked POs). Staged queue is an outbox, not a ledger — must be flushed once live. **The portal never creates purchase.order or product.product records** — POs and products are created in Odoo and linked in the portal (suppliers via `odoo_partner_id`, 13.0.7; products via `odoo_product_id`, 13.0.8); a PO-less receipt fails sync with a clear message. Every op builder carries `product_code`/`product_id`; `_product_id_for()` uses the pinned id when present, else falls back to a name match (`_resolve_product()`) labelled clearly as a fallback. `production_routes.py::_refresh_product_pins()` re-resolves `product_id` from the CURRENT link immediately before every `execute_ops()` call (live writes and both `sync_staged` loops) — so an op staged before a product was linked still resolves correctly once it is, with no re-creation needed.
- `frontend/src/views/BatchRegistry.js` — `/production/batches`: generator hero (family + product picker, live ID preview, zero typing) — **Bassani-produced batches only**; imported (BI) batches are never generated here (a compliance decision — see `production_routes.py::create_batch`), only ever created inside the S6 Receiving flow (`receive_import`), atomically with the `s6_receipts` quarantine record; the hero links to the S6 Receiving page for imports. The master list is called **Products** everywhere (Bassani's own sheet is "Shortcode for products" — it mixes strains, gummy flavours, vapes, oils); "strain" is only used where it genuinely means the flower strain (e.g. the Single Strain batch type). ## Key Business Rules

**Reseller model:**
- Resellers are external business partners who place orders on behalf of their own customers.
- Each reseller can only place orders for customers linked to their profile (onboarded by them or linked by an admin) — enforced server-side, not just by the frontend's pre-filtered customer picker (7.13).
- Resellers have a read-only product catalog view — they never see stock history, barcodes, or admin controls.
- **Visibility and commission are both governed by customer ownership (`customer_ownership`), not by who physically placed the order (7.13).** A reseller sees and can act on every order/ticket for a customer linked to them — including ones Bassani staff placed directly on that customer's behalf — exactly as if they'd placed it themselves. Commission works the same way: a reseller earns commission on all of a linked customer's orders, not just ones they personally placed. The one exception is retroactivity: linking an existing customer to a reseller never generates commission for that customer's past orders — only orders confirmed from the link date forward, guaranteed by construction (commission records are only ever created going forward at confirm time, resolved fresh against current ownership each time) rather than by a date comparison. `order.reseller_id`/`ticket.reseller_id` ("who placed this") still exist and are still shown for traceability (8.34) — they're just no longer used for access control or commission crediting. See `backend/ownership.py`.
- Commission is calculated as a percentage of monthly turnover using configurable tier bands. The `commission_eligible` flag is checked at order confirmation time: orders confirmed while the flag is off produce no `order_commissions` record and will never appear in any statement. Toggling the flag off does not retroactively affect past confirmed orders.
- **Place Order vs Save as Draft (2026-08-21) — superseded the old "staff must review before confirm" default.** A reseller/customer order still lands as a `quote`-status ticket if **Save as Draft** is used, visible to Bassani sales staff to assign/track/confirm exactly as before. But **Place Order** (the primary cart button, both roles) now runs the order through the same stock-check-review-then-confirm chain the standalone order-detail "Confirm Order" action always had (`GET /orders/{id}/stock-check` → review modal → `PUT /orders/{id}/confirm`), immediately after creation — so a reseller's order typically never rests at `quote` at all, moving straight to `awaiting_deposit` without a Bassani staff touchpoint. This was a deliberate reversal of the previous "resellers always land in a staff queue" design, confirmed with the product owner: the portal's own stock-check and credit-check already do what that manual staff review existed to catch, making the extra step redundant. Staff still see and can act on every order once it's past `quote` (Orders Monitor, Sales Tickets, etc.) — what's removed is only the mandatory pre-confirm pause, not visibility. A reseller/staff credit-limit block still offers "Confirm Anyway" (mirrors `SalesTickets.js`'s existing override pattern); a customer never gets that override and is told to contact Bassani, same as the standalone customer confirm flow. Cancelling out of either the stock-check or credit-override modal never loses the order — it was already created as a draft the moment Place Order was clicked, so cancelling just leaves that draft in place, identical to having clicked Save as Draft. Implemented entirely in `Views.js::Orders()`'s cart (`submitCart`/`runCartConfirmChain`/`finalizeCartConfirm`) — no new backend endpoints, just chaining the existing `create_order` → `stock-check` → `confirm` calls that already existed as three separate manual steps.
- **Recurring order setup built into checkout (2026-08-21):** a "Make this a recurring order" checkbox in the cart footer (both roles, new-order mode only — not `editQuote`) collects the same cadence/end-condition fields `RecurringOrderSetupModal.js` does, and fires `POST /api/recurring-orders` right after order creation using the `ticket_id` `create_order` now returns in its response (previously the caller had no way to know the newly created ticket's id at all). Fires regardless of Place Order vs Save as Draft — the recurring engine re-fetches its own pricing and creates its own ticket at each occurrence (8.46), so the source order's confirm state has no bearing on it. Non-fatal: a failure here doesn't undo the order, just surfaces a toast pointing at the order's own page to retry. Order Passport's existing "Make Recurring" button (8.46/25.1) is unchanged and still the way to set this up after the fact for an order that wasn't flagged at checkout.
- Resellers receive email notifications at key pipeline milestones: order placed, order confirmed, packing started, and ready for collection (full delivery). Partial-delivery backorder notifications also fire.
- **Customer-role notification parity (2026-08-22):** a customer-role account (Phase 25) placing and confirming their own order previously received no mid-pipeline email at all beyond the deposit-due proforma (which already goes straight to the ordering company regardless of role) and the final "Ready for Collection" notice (`send_order_ready_for_collection_customer`, 8.49) — "Order Confirmed" and "Packing Started," reseller-facing milestones, are both gated on `reseller_id`/commission-link presence and never reached a customer-placed order. **Deliberately not full parity** — a customer only gets one additional email, the partial/backorder confirmation (`send_order_confirmed_partial_customer`, `order_routes.py::_queue_packing_board`), sent independently of the reseller notice via the same `_resolve_customer_notification_recipients` lookup (`packing_board_routes.py`) the Ready for Collection notice already uses. "Packing Started" was deliberately left reseller/staff-only — it's internal warehouse status, not something an end customer needs to act on or be told; "Order Confirmed" (non-partial) needs no separate customer email since the proforma already serves that purpose with something actually actionable (the deposit amount due). Configurable as a preview-only entry (`order_confirmed_partial_customer`) under Settings > Email Notifications > Orders & Fulfilment, same shape as `order_ready_customer` — always routes to the resolved customer, no staff recipient list to configure.
- **Sales Agent profiles support both companies and individuals.** The Add/Edit Sales Agent wizard (`Resellers()` in `Views.js`) has an optional Legal Entity Type field (Private Company (Pty) Ltd / Close Corporation (CC) / Sole Proprietor / Partnership / Other — same list as the customer wizard's `PublicRegister.js`). Leaving it unset renders the wizard exactly as before (company-style fields). Selecting Sole Proprietor swaps the Company Reg Number field for an ID/Passport Number field: a Document Type selector (South African ID / Passport, `id_type` on the reseller doc, defaults `"sa_id"` for pre-8.52 records with none stored) picks which validator runs — `validateSAID` (Luhn-checked) for an SA ID, `validatePassport` (length/format only, no checksum exists) for a passport (both `frontend/src/utils/validators.js`, 8.52). VAT and banking details stay unconditional for every entity type since banking is where commission is paid out regardless of legal structure. Selecting an existing Odoo vendor partner in Step 1 auto-fills name/email/phone/seller_code as before, plus VAT number (from Odoo's `vat` field, now included in `CUSTOMER_FIELDS`) — it does not touch entity type or address, which stay manual/unset respectively.

**Customer self-service accounts (Phase 25, 2026-08-21):** Already-approved customers can log into the portal themselves — place their own orders, build their own quotes, view their own invoices — through the exact same pipeline as everyone else. Distinct from the reseller model in three ways: (1) provisioning is **admin-initiated, opt-in**, never automatic — an admin grants access per Odoo contact from the customer profile page ("Enable Portal Access"), gated by the dedicated `customers.manage_portal_access` permission (off by default even for `sales`, which already has `customers.manage`); (2) **one company can have several logins**, one per Odoo child contact (an individual customer gets exactly one, on their own partner record) — every login under a company shares the same order/invoice history, scoped to `users.customer_company_partner_id` (the commercial partner), not the individual contact; (3) a `customer` account **never earns commission** — enforced structurally by never creating a `resellers` doc for one, not by a role check. If the customer's company is linked to a reseller via `customer_ownership`, that reseller keeps earning commission on all the customer's orders exactly as if a reseller or staff member had placed them — this required no new code, since commission crediting at confirm time was already keyed off `customer_ownership`, never off who placed the order (see the Reseller model bullets above). A customer's warehouse scoping defaults to the global admin default, overridable per company (`customer_metadata.warehouse_id`, same pattern as the existing `samples_account` flag) — it does not inherit a linked reseller's warehouse. See `backend/routes/customer_routes.py`'s portal-access endpoints and `backend/warehouse_context.py`'s customer branch. **Product visibility and self-service confirm (fixed 2026-08-21):** a customer abides by the exact same product-catalog rules as a reseller — restricted to the curated `reseller_catalog` allowlist in `product_routes.py` (`list_products`/`list_categories`/`get_product_by_barcode`, keyed on `role in ("reseller", "customer")`), not the full Odoo catalog. A customer can also confirm their own placed order (`PUT /orders/{id}/confirm`, `_require_confirm_access` + an ownership check inside `_confirm_order_core` mirroring the reseller one) from a "Confirm Order" action on their own Orders detail page — deliberately not the Sales Ticket pipeline UI, which stays staff/reseller-only. Confirming runs the same stock-check-first flow staff/resellers use, except a credit-limit block (`402`) is never offerable-to-self-override for a customer — they're told to contact Bassani, unlike staff/reseller who see a "Confirm Anyway" option. This also surfaced and fixed a pre-existing bug affecting resellers too: `GET /orders/{id}/stock-check` was gated by `require_permission("orders.read")` — not a real permission key, and reseller isn't in `require_permission`'s allowed role set at all — so it 403'd for every reseller silently (the frontend's `catch` swallowed the failure and confirmed straight through with no stock-check modal ever shown). Fixed by reusing `_require_confirm_access` (moved earlier in the file so the dependency reference resolves) plus the same per-order ownership check.

**Multi-company customer logins (2026-08-21):** a customer's email can legitimately be linked to more than one Odoo company — the same person can be a contact, or the company record itself, on several separate companies, the same "same contact, multiple branches" pattern the onboarding section above already documents. One login now holds a `companies: [{odoo_partner_id, customer_company_partner_id, company_name, active}]` array plus `active_company_partner_id` (mirrors `active_warehouse_id`'s shape exactly), rather than the single fixed `customer_company_partner_id` field described above. **Every existing backend read of `current_user.get("customer_company_partner_id")` across the codebase (orders, invoices, dashboard, recurring orders, warehouse scoping) needed zero changes** — `customer_company_partner_id`/`odoo_partner_id` are now derived fresh on every request by `auth.py`'s `resolve_customer_active_company()` (called from `get_current_user()`, and separately from `login()`/`verify_otp()` in `auth_routes.py` since those run before a `get_current_user` cycle exists), always reflecting whichever `companies[]` entry `active_company_partner_id` currently points at. Self-heals onto another active company if the pointer is stale, unset, or revoked mid-session, or to `None` (denying every ownership check) if the login has zero active company grants left — a login is never left silently serving a revoked company's data. A `PUT /api/users/me/active-company` endpoint (`user_routes.py`, next to `set_active_warehouse`) lets the customer switch which company is active; `CompanySwitcher` (`UI.js`, mirrors `WarehouseSwitcher`, rendered unconditionally in `TopBar`) shows a dropdown for **every** customer login, even one with only a single company (2026-08-21 follow-up — the select is simply `disabled` when there's nothing to switch to), so every customer sees which profile they're placing an order under and the app bar looks identical across single- and multi-company logins, rather than the switcher appearing only once a second company exists. Unlike `WarehouseSwitcher` (`hidden sm:flex`, staff-only), `CompanySwitcher` has no such mobile hiding — it's the one thing the mobile app bar prioritises showing for a customer login, alongside a matching mobile cleanup (`WarehouseLabel` now `hidden sm:inline-flex`, and the order cart's Back button now `hidden sm:block` entirely — the hamburger menu already reaches every other page on mobile, so it's not missed) that fixed a real overflow bug: the warehouse badge and full-text Back button together ran off the edge of a phone-width app bar. **Removed outright for the customer role (2026-08-21, explicit request), not just hidden on mobile:** `WarehouseLabel` in the order cart (`!isCustomer &&` guard, `Views.js`) — the company switcher already communicates which account an order is under, and which warehouse fulfils it is an internal detail; and `TopBar`'s "Odoo synced"/"Odoo offline" badge (`user?.role !== "customer"` guard, `UI.js`) — this is also, independently, the one place in the app that violates the standing "never expose Odoo to external roles" rule for a role still shown it (resellers still see this badge; not touched in this pass since only the customer removal was requested — flagged here as a known, not-yet-fixed instance of that rule). `customer_routes.py`'s `grant_portal_access` now looks up an existing customer-role login by email before failing: a brand-new email creates a login as before; an email that already has a customer login for a *different* company gets that company **pushed onto its existing `companies[]`** instead (no second password, a distinct `send_customer_company_added` email instead of the set-password invite); an email belonging to a staff/reseller login still hard-blocks, unchanged. `get_portal_access` surfaces this ahead of time too — each candidate contact gets a `linked_elsewhere` list (now including `odoo_partner_id`, not just the company name/id) when its email already has active access elsewhere, shown as an inline warning in `CustomerProfile.js`'s Portal Access table with a confirm step before granting (skipped entirely when there's no overlap). **That confirm dialog lists every other linked company as a checkbox, checked by default** — unchecking one deactivates it (via the same per-company deactivate endpoint) in the same action as the grant, so an admin can exclude a duplicate or phased-out profile from the login's switcher right there, instead of granting first and then hunting down a separate deactivate action on that other company's own profile page afterward. `deactivate_portal_access`/`reactivate_portal_access` now toggle one `companies[]` entry's own `active` flag (via a Mongo arrayFilters update) rather than the top-level `users.active` — revoking one company must never lock the login out of its other companies; the top-level flag remains a separate, explicit "suspend the whole account" control. The old partial-unique index on flat `odoo_partner_id` was replaced with a partial-unique **multikey** index on `companies.odoo_partner_id` (`server.py`), preserving "one Odoo contact record backs at most one login" now that the field lives inside the array — a one-time idempotent startup migration wraps any pre-existing flat-shaped customer docs into the new shape.

**Customer onboarding:**
- Resellers initiate customer onboarding via a 5-step wizard (Step 0 gates: send/download template docs, Step 1: company details, Step 2: contact, Step 3: banking, Step 4: documents).
- Applications go to an admin review queue. Approval creates the customer in Odoo and links them to the reseller.
- Onboarding documents are stored in R2. Admin can also upload documents directly to a customer profile.
- Admins can link existing Odoo customers to a reseller or unlink them. Both actions are audit-logged.
- **Same contact, multiple branches (confirmed 2026-08-04):** one person being the signatory/contact on more than one application is expected and common for this business — one owner running several stores, sometimes as separate legal entities with distinct CIPC docs, sometimes as multiple branches of the same legal entity (identical CIPC docs, different trading names, often no VAT number). `approve_application` does **not** block on the contact email matching an existing Odoo partner/contact — each application still gets its own `res.partner` company record, and the contact still gets their own child contact record under it (Odoo's `parent_id` is single-valued, so "the same contact on two companies" is modeled as two separate contact records sharing the same name/email, not one shared record — this is the standard Odoo pattern, not a workaround). What **does** still block approval: a matching VAT number (a real same-legal-entity signal), or the exact same `company_name` + `trading_name` combination already approved (guards against an accidental literal resubmission of the same branch) — see `approve_application_link` for the existing "link to this existing partner instead of creating a new one" resolution path when either of those genuinely fires. When the contact email does match an existing partner, that's recorded as an informational `linked_contact_note` in the `onboarding.approve` audit log entry, not a blocker. Because two branches of one legal entity (e.g. "Cannapure Plus NPC" in both Witbank and Dullstroom) would otherwise be indistinguishable everywhere the customer name is shown, the Odoo partner's `name` field folds in the trading name when it differs from the company name (`"{company_name} - {trading_name}"`) — the plain legal entity name alone is not used as the display name in this case.
- **Self-service registration:** Public route `/apply` — customers register without staff involvement. Reseller referral links use `?ref=RESELLER_CODE`. Customer signs only the Customer Information Form in-browser + uploads their non-signed supporting document(s). NDA and Store Onboarding Agreement are sent separately by admin after review. The wizard is 5 steps: (0) **Registering as** business/individual toggle (8.50), then Business Details — three fields at top: **Business Category** dropdown (Pharmacy, Dispensary, Wellness Centre, Medical Clinic, Health Retailer, Other + text input), **Legal Entity Type** dropdown (Private Company (Pty) Ltd, Close Corporation (CC), Sole Proprietor, Partnership, Other + text input), **Section 22C Licensed Facility** checkbox. Legal Entity Type drives form adaptation: Sole Proprietors see no Company Reg or Trading Name fields, "Registered Company Name" label becomes "Business / Trading Name"; (1) Primary Contact — ID or Passport required (8.52: Document Type selector, `signatory_id_type` — SA ID is Luhn-validated via `validateSAID`, Passport is a length/format-only check via `validatePassport` since passports have no universal checksum), position required (skipped for individuals), SA phone format enforced; (2) Business Address — suburb, province, and postal code all required, postal code validated as exactly 4 digits; (3) Additional Info; (4) Sign Documents. Backend `PublicRegistration` model stores `business_category`, `business_category_other`, `entity_type`, `entity_type_other`, `section22c_licensed`, `signatory_id_type`. `business_type` field kept as Optional for legacy application records. The individual flow's non-signed ID-document upload hint (`UPLOAD_DOCS.individual`) also accepts a passport, not just an SA ID. `signatory_id_type` defaults `"sa_id"` for pre-8.52 applications with no stored value, so existing records display unchanged. The value written into Odoo (individual `res.partner` notes / business signatory contact `comment`) is labelled `"SA ID:"` or `"Passport:"` accordingly (`onboarding_routes.py::_signatory_id_label()`) rather than always assuming SA ID.
- **Individual (natural-person) registration (8.50, added 2026-08-04):** Self-service `/apply` only — a private individual (a named patient with a Section 21 outcome letter) can register with `registration_type: "individual"` instead of the default `"business"`. Step 0 collapses to just the toggle (no company fields at all); the non-signed document requirement swaps CIPC for an ID document + Section 21 outcome letter (`UPLOAD_DOCS` config in `PublicRegister.js`, `INDIVIDUAL_DOC_TYPES` in `public_routes.py`/`onboarding_routes.py`). CIF, NDA, and Store Onboarding Agreement are still signed exactly the same way as a business application. On approval, an individual becomes a single standalone Odoo `res.partner` (`company_type: "person"`) with no separate child contact — the applicant IS the contact, unlike a business's company+signatory split. Duplicate-check is ID-number-based (blocks on a second approved individual application with the same `signatory_id_number`) rather than the business flow's VAT/trading-name checks, since one person registering twice is presumptively a duplicate, not a legitimate second branch. The reseller-initiated onboarding wizard (`CustomerOnboarding.js` / `submit_application`) was not extended to individuals — business-only, unchanged. An optional **Diagnosis / Indication** field (Step 3, individual only) captures the patient's condition for internal use; on approval it's persisted to `customer_metadata` (keyed by `odoo_partner_id`) so it stays with the ongoing customer record, not just the application. This is deliberately the only extra compliance-adjacent field added so far — a broader SAHPRA/Section 21 checklist (prescribing doctor details, authorised product/quantity, approval expiry, delivery conditions) was discussed and intentionally left out pending RP/compliance sign-off; see the Section 21 authorisation note below.
- **Full onboarding flow:** (1) Customer submits `/apply` → CIF signed in-browser + supporting document(s) uploaded (CIPC for a business; ID document + Section 21 outcome letter for an individual) → application created in `pending` state. (2) Admin receives email with a direct link to the specific application. (3) Admin reviews CIF + the uploaded document(s) on the application detail page. (4) Admin clicks **Generate Documents** → `POST /generate-signing-docs` creates a `signing_sessions` MongoDB doc (status: `"generated"`) with a 30-day UUID token and a form_data snapshot — no email sent yet. (5) Admin previews the pre-filled NDA and SOA in-browser (client-side PDF rendering via `generateSignedPdf`). (6) Admin clicks **Send to Customer** → `POST /send-signing-docs` sends `send_signing_invitation` email; session status updated to `"sent"`. (7) Customer opens `/sign/{token}` (public, no auth), signs NDA + SOA in-browser; each signed PDF stored in R2 and stamped onto the application with `signed_in_portal: true`. (8) Signing authority claims the application and countersigns each document in-portal. (9) When both NDA + SOA are countersigned, a notification is sent to recipients configured in the `countersign_complete_to` email routing key (typically Kashi and Dean). (10) Dean (or any `customers.approve_onboarding` user) clicks **Approve & Send Welcome Pack** (8.55, one combined action, `PUT /approve-and-send-welcome-pack`) → Odoo customer created, all docs transferred to `customer_documents`, **and** the welcome pack email sent in the same step: attaches all onboarding documents (CIF, the business/individual document(s), countersigned NDA, countersigned SOA) plus the four active Welcome Pack slot files (Help Me Budget, Welcome Letter, Price List, Product Brochure). **Order pipeline:**
- Reseller places order (or a direct-inquiry quote is confirmed) → Sales ticket created → **staff/reseller confirms the order → `awaiting_deposit` → Finance registers a 50% deposit → packing board ("order ticket") is created** → Orders clerk confirms packing → QA approval → RP approval → Invoice created → Finance confirms payment → Complete.
- **Deposit gate (8.47, reinstated 2026-07-29 — a deliberate reversal of 8.39's removal):** A 50% deposit is a hard, universal requirement — **no exceptions for any order, reseller or direct, credit terms or not.** `PUT /orders/{order_id}/confirm` (`_confirm_order_core`, `order_routes.py`) confirms the order in Odoo and advances the linked ticket to `awaiting_deposit`, but does **not** create the packing board entry. Only `POST /api/tickets/{id}/register-deposit` (`ticket_routes.py`) — which creates+posts a down payment invoice via Odoo's `sale.advance.payment.inv` wizard and registers payment via `account.payment.register` — calls `_queue_packing_board()` (`order_routes.py`) to actually create the packing board entry and advance the ticket to `confirmed_wip`. This is the single, non-bypassable gate: there is no admin-override path to *skip* it (the old `admin-override-payment` endpoint, which could queue packing without any payment, was deleted as part of reinstating this gate — keeping it would have silently defeated the requirement). The Odoo-state auto-sync path in `ticket_routes.py` (for orders confirmed directly in Odoo, bypassing the portal) routes through the same `awaiting_deposit` stage rather than auto-queuing packing, so it can't bypass the gate either. **Recovery path (2026-08-11):** if `_queue_packing_board()` fails after a deposit genuinely was registered (most commonly Odoo not having generated the delivery yet), `update_ticket_stage`'s Admin Override can retry it by setting the ticket to `confirmed_wip` — but only ever as a retry: it hard-blocks with a 400 ("Admin Override cannot skip this gate") unless `ticket.payment_confirmed_at` is already set (or the ticket `is_sample`), so this can never become a second way to reach the packing board without a deposit.
- **Proforma invoice (8.47):** The moment an order is confirmed, the portal automatically fetches Odoo's native Pro-Forma Invoice report (`sale.report_saleorder_pro_forma`, requires Odoo's Pro-Forma Invoice feature enabled in Sales settings) via `odoo_client.py`'s `fetch_report_pdf()` and emails it to the customer stating the 50% amount due, via `send_deposit_due_proforma()`. Non-fatal — a missing/disabled report degrades to a warning, never blocks confirmation. **Fixed 2026-08-14:** previously fetched via `odoo.execute("ir.actions.report", "_render_qweb_pdf", ...)` — a direct XML-RPC call to a private Odoo method — which Odoo started hard-rejecting ("Private methods ... cannot be called remotely"), silently killing every proforma email until noticed. See `odoo_client.py`'s `fetch_report_pdf()` entry above for the fix (session-based HTTP, the same mechanism Odoo's own UI uses) and why the report name also had to change. **Reseller CC fixed 2026-08-21:** the CC address is resolved via `get_owning_reseller_id()` (`customer_ownership`) — the same lookup the commission-crediting block uses a few lines above it — not `sales_ticket.reseller_id` ("who placed this"). The old field-based check meant a customer's self-placed order (Phase 25) never CC'd its linked reseller even though that reseller still earns commission on it; ownership-based CC means "whoever earns commission on this order sees the deposit invoice," regardless of who placed it.
- **Invoice timing:** The full delivery invoice (separate from the deposit down-payment invoice) is created and posted in Odoo at `mark_complete` on the packing board (after QA + RP have both signed off) — unchanged from 8.39. This is the "ready for collection" point. Finance confirmation checks Odoo's real invoice `payment_state` — it is not a disconnected checkbox. As of 2026-08-04, the invoice is also automatically emailed to the customer at this point (same Odoo `mail.template`/`send_mail` mechanism as the pre-existing manual "Send Invoice" button in `ticket_routes.py`) — non-fatal, degrades to a warning if Odoo has no invoice mail template configured. `ticket.invoice_sent_at` is stamped either way it was sent, so the manual button correctly shows "Resend Invoice" afterward.
- **Customer/reseller Proof of Payment upload (2026-08-21):** self-service, on the order's own Order Passport page — deliberately evidence and a trigger only, never an automatic payment registration. Finance still explicitly clicks Register Deposit/Register Balance Payment afterward, same as always, preserving the "no exceptions" deposit gate and the real bank-reconciliation-based verification this portal relies on; a POP upload just gets the ticket in front of Finance faster than being told outside the portal. `POST /api/tickets/{id}/pop` (`ticket_routes.py`) is the first customer-role branch anywhere in that file — a new `_require_ticket_uploader` dependency pass-throughs `role in ("reseller", "customer")` (mirroring the existing reseller-only pass-throughs `_require_ticket_viewer`/`_require_ticket_driver`), with ownership checked via the same `customer_company_partner_id` equality used throughout every other customer branch this session. Stored as `tickets.pop_uploads[]` (R2, same upload shape as `customer_routes.py::upload_customer_document`) plus a `pop_awaiting_review` flag that drives an amber "POP Uploaded" badge on the Sales Tickets list (independent of the existing green "Confirmed" badge — a ticket can have its deposit already confirmed while a *new* upload for the balance is still awaiting review) and a real-time email (`pop_uploaded_to` routing key). The flag clears automatically the moment Finance registers a payment through any of the ticket's four existing payment-confirming code paths (`register_deposit`, `register_balance_payment`, `use_existing_invoice`, the Odoo-state `confirm_payment` sync), or manually via a new "Mark POP Reviewed" action for the no-payment-needed case (duplicate upload, handled another way) — same `tickets.finance_confirm` permission that already gates the payment actions, no new permission added. The customer-facing UI is explicit that this step is optional ("Bassani will still confirm your payment through the usual process either way") so it never reads as blocking their order.
- **Mark as Collected (fixed 2026-08-04):** After `mark_complete`, the packing board entry sits at `status: "complete"` (frontend label: "Ready for Collection" — deliberately not "Complete", since that word is also the ticket's separate terminal `exit_status`, and the two were showing the same word for two different pipeline stages, which read as a stuck/duplicate order). An Orders Clerk must explicitly click **Mark as Collected** (`OrdersTickets.js`, `PUT /api/packing/mark-collected`) once the customer physically collects the order — this is what advances the ticket to its true terminal `exit_status: "complete"`. This button was previously gated on `has_pending_invoice`, a flag only ever set for partial/backorder deliveries — meaning it never appeared for a normal, single-delivery order (old or new alike). The backend endpoint never required that flag; the gate was purely a frontend bug. Fixed by dropping the `has_pending_invoice` condition so the button shows for any complete, uncollected order. **Second, deeper layer of the same bug (also fixed 2026-08-04):** the entire "Role-gated action cards" sidebar in `OrdersTickets.js` — every action on the detail page, not just Mark as Collected — is wrapped in a single `{!isTerminal && (...)}` check, and the page's own `TERMINAL` status set incorrectly included `"complete"` alongside genuinely terminal states (`collected`/`incomplete`/`cancelled`/`cleared`). - **Partial fulfilment / backorders:** `GET /api/orders/{order_id}/stock-check` returns `is_partial`, `lines` (ships now vs backordered), `invoice_policy_block`, and `invoice_policy_blocked_products`. Shortfall detection is now performed at deposit-registration time (`_queue_packing_board`), not at confirm time — stock reservations can shift while a deposit is pending, so this is recomputed fresh rather than reusing a confirm-time snapshot. **Fixed 2026-08-11 — root cause was Odoo version drift, not a portal bug:** the reserved-quantity read (`stock.move.reserved_availability`) was invalid on the live Odoo instance — `ValueError: Invalid field 'reserved_availability' on 'stock.move'`. Investigation (live `fields_get`/`read` probes against production, read-only) found the live instance is actually **Odoo 19.0**, not the v17 documented everywhere in this file at the time — the third-party host had upgraded it at some point with no corresponding update here. Odoo 19 replaced the old `reserved_availability` (pre-pick reserved amount) and `quantity_done` (post-pick done amount) with a single unified field, **`quantity`**, whose meaning is state-dependent: `0` while nothing is reserved yet (`waiting`/`confirmed`), the actual reserved amount once partially or fully reserved (`partially_available`/`assigned` — confirmed live: equals `product_uom_qty` exactly when fully reserved, less than it when partial), and the actual transacted amount once `done`. Verified against real moves in every one of those states before shipping the fix, and re-verified against the exact order from the original incident (S00764 / picking 910) post-fix. All `reserved_availability` and `quantity_done` reads in `order_routes.py` now use `quantity` — this also fixed two other silently-broken (swallowed by an enclosing `try/except: pass`) features that shared the same root cause: the Order Passport's Deliveries section and its per-line MO/backorder breakdown had been returning empty for every order. **This means shortfall/backorder detection, which had never actually worked since 8.47 shipped (always silently returned "no shortfall"), is now genuinely functional for the first time** — treat any backorder/partial-fulfilment behavior observed before 2026-08-11 as unverified.
- **Out-of-stock items are orderable, not blocked (fixed 2026-08-21):** `order_routes.py::create_order` previously hard-rejected the entire quote/order (400) if any line's requested quantity exceeded `virtual_available`, for every role. This was a separate, stricter gate than the confirm-time stock-check/backorder flow above, and directly contradicted Bassani's requirement that customers be able to order an out-of-stock item so it can be fulfilled as a backorder. Removed the hard block; a shortfall is now surfaced as a non-blocking `stock_warning` string in the response (same pattern as the existing `credit_warning`), toasted client-side. - **Critical fix, found live 2026-08-21 — customer's own order list was silently warehouse-filtered:** reported by the product owner testing a real customer login ("I can't see any of my orders — is it only showing what I create?"). Root cause: `order_routes.py::list_orders` applies a warehouse domain filter for every role, and `resolve_warehouse_id()`'s customer branch can basically never return `None` — it falls back to the global admin default the moment one is configured. So a customer's order list was silently restricted to whichever single warehouse they're scoped to, hiding any order fulfilled from a different one — including ones Bassani staff placed on their behalf, directly contradicting the "every login sees the whole company's history" design this phase was built on. Fixed by skipping the warehouse filter entirely for customer role in `list_orders` (staff/reseller behaviour unchanged) — warehouse is an internal fulfilment detail, not a customer-facing scoping boundary. `list_invoices` was **not** affected — it never applied a warehouse filter — and `get_order`/`get_order_passport` (single-order lookups by id) don't call `resolve_warehouse_id` at all, so direct-link/passport access to a specific order was never affected either; only the list view was broken. `resolve_warehouse_id()` itself is untouched — it's still correctly used to scope stock/catalog browsing for placing a *new* order, which is a legitimate, different use case from viewing order *history*.

**Recurring orders (Phase 8.46):**
- A direct-inquiry Sales ticket or a reseller order can be flagged recurring once it has a linked order (line items are the template) — "Make Recurring" on the ticket detail page (`RecurringOrderSetupModal.js`), `POST /api/recurring-orders` (`recurring_order_routes.py`). **Batch traceability (Phase 13):**
- Bassani's batch ID schema is fixed: `BH` + `API`/`B` + strain code + sequence + date (e.g. `BHAPIBBY-001-010126`). Suffixes: `-D` Drying, `-U` Unmanicured, `-M` Manicured, `-P` Pops, `-T` Trim. - **External imports (built 2026-07-27, from the S6 Stock Receiving Logbook):** fifth prefix family — `BI{supplier}-{product}{type_digit}{import_ref:02d}{subcat?}-{DDMMYY}`, e.g. `BISB-JSY340L-300426` (Seven Blade / Jealousy / Greenhouse / ref 40 / Large). 13 supplier shortcodes in `import_suppliers`; type digits 1 Indoor / 2 Greendoor / 3 Greenhouse / 4 Distillate / 5 Vape / 6 Hash / 7 Edible / 8 Tincture / 9 Trim; stable per-product `import_ref` auto-assigned on first import; optional size char L/P/S. Implemented in `build_import_batch_id()` (services/batch_id.py) — never re-derive. Stage suffixes apply to BI bases unchanged.
- **Stage suffix assigned at creation, not left bare (2026-07-28):** BH flower families (`single`/`api`/`blend`) always get `-U` baked in the moment the batch is generated (`FLOWER_FAMILIES` in `production_routes.py`) — Track A starts at the vault door (dried, unmanicured bulk), so there is no meaningful "no suffix yet" state to represent; Gummy stays bare (no manicuring stage). Imports get their stage from `_determine_import_stage()`: subcat Large/Smalls → `-M`, Pops → `-P`, stock type Trim → always `-T`, Distillate/Vape/Hash/Edible/Tincture → no suffix; the *only* case requiring an explicit answer is a flower-type import with no size given (S6 Receiving form asks "already manicured?" — required, no default). `base_batch_id` is always stored as the pre-suffix root regardless of which suffix the first entry carries, so registry grouping and later `-U`→`-M`/`-T` derivation via `derive_stage_id()` are unaffected. **Important consequence:** `base_batch_id` no longer always equals a real document's `batch_id` — any code that looks something up by `base_batch_id` must not assume a document exists under that exact string (see `GET /batches/{id}/timeline`, the quarantine gate's `s6_receipts` lookup in `create_movement`, and `vault_ledger`'s `unreleased_imports`, all fixed same day to handle this).

## Phase 13 — Compliance Notes

Phase 13 (Production and Cultivation Module) must be built to EU GMP Annex 11 (Computerised Systems) standards, which SAHPRA aligns with for medicinal cannabis.

**Already satisfied by the existing portal:**
- Named users and roles (Phase 0)
- Comprehensive audit trail with actor, timestamp, and before/after (Phase 0.6)
- Secure API with JWT and 2FA (Phase 1.5)
- Regular MongoDB backups (Railway)
- Incident management via Sentry (Phase 6)

**Critical gap — Electronic Signatures (Annex 11 §30-31):**
A JWT-authenticated button click does not satisfy Annex 11. Re-authentication at point of critical sign-off (QA/RP approval, batch release) is required. The e-signature module must: re-verify password at sign-off → verify bcrypt independently of JWT → create a permanent `signature_event` document linked to the record. This affects Phase 13 and is a retrofit on the existing packing board QA/RP approvals.

**Before starting Phase 13:** obtain SAHPRA's specific submission format and get compliance officer confirmation of Annex 11 requirement. The batch ID schema and traceability chain are already fixed — do not re-derive them.
